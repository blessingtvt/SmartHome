## 1. 项目整体架构

### 1.1 顶层组成

系统由 **6 类运行时组件** 组成：

| 组件 | 名称 | 端口 | 技术栈 | 职责 |
|---|---|---|---|---|
| 家属端前端 | frontend | 5173（Vite dev） | Vue 3.4 + Vite 5 + Element Plus + Pinia + Vue Router + Axios + ECharts | 五个页面，家属查看/控制入口 |
| 统一网关 | gateway-service | 8080 | Spring Cloud Gateway（WebFlux） | 统一对外入口，`lb://` 路由到各微服务 |
| 服务注册发现 | Nacos | 8848 | Spring Cloud Alibaba Nacos Discovery | 服务注册与发现，供网关 `lb://` 解析 |
| 微服务 S1 | environment-service | 8081 | Spring Boot 3.2.4 | 环境数据采集、家庭/房间管理 |
| 微服务 S2 | rule-service | 8082 | Spring Boot 3.2.4 | 自动化规则评估与执行 |
| 微服务 S3 | device-service | 8083 | Spring Boot 3.2.4 | 设备/指令管理、心跳、在线判定 |
| 微服务 S4 | alarm-service | 8084 | Spring Boot 3.2.4 | 告警管理、一键求助 |
| 数据库 | MySQL 8 | 3306 | MySQL + MyBatis-Plus | 持久化（库名 `smart_home_db`） |
| 老人端硬件 | ESP32 固件 | —（HTTP 客户端） | Arduino C/C++（HTTPClient + ArduinoJson） | 采集传感器、执行指令、一键求助 |

后端统一技术栈：**Java 17、Spring Boot 3.2.4、Spring Cloud 2023.0.1、Spring Cloud Alibaba 2023.0.1.0、MyBatis-Plus 3.5.7、MySQL 8**。

### 1.2 模块结构（Maven 多模块）

```
smart-home/
├── gateway-service/        # G0 网关（8080）
├── environment-service/    # S1 环境服务（8081）
├── rule-service/           # S2 规则服务（8082）
├── device-service/         # S3 设备服务（8083）
├── alarm-service/          # S4 告警服务（8084）
├── smart-home-common/      # 公共模块（Result<T>、BusinessException、常量、VO 等）
├── frontend/               # Vue 3 家属端（独立子项目，不进 Maven）
├── esp32-firmware/         # ESP32 固件（独立子项目，不进 Maven）
├── database/               # schema.sql 与迁移脚本
└── docs/                   # 开发文档
```

公共模块 `smart-home-common` 提供统一响应 `Result<T>`（`code/message/data`，`code=200` 为成功，**HTTP 状态码恒为 200**）、`BusinessException(code,msg)`、`GlobalExceptionHandler` 全局异常处理。

### 1.3 服务间通信方式（关键）

系统存在 **两条不同的调用链路**：

1. **对外链路（经网关）**：前端 / ESP32 → Gateway(8080) → 按 Path 谓词 `lb://service-name` 路由（经 Nacos 发现解析 IP）→ S1~S4。
2. **服务间内部链路（直连，不走网关、不走 Nacos）**：S1 → S2、S2 → S3、S2 → S4 之间使用 **Spring `RestClient` 直连 `http://127.0.0.1:端口/internal/...`**。

具体内部调用关系：

| 调用方 | 目标 | 地址 | 接口 |
|---|---|---|---|
| S1 environment-service | S2 rule-service | `http://127.0.0.1:8082` | `POST /internal/rules/evaluate` |
| S2 rule-service | S3 device-service | `http://127.0.0.1:8083` | `POST /internal/device-commands`、`GET /internal/devices/{code}/state`、`GET /internal/device-commands/{id}` |
| S2 rule-service | S4 alarm-service | `http://127.0.0.1:8084` | `POST /internal/alarms` |

- 这些 `/internal/**` 接口 **不对网关暴露**（网关路由谓词未配置），仅服务间内部使用。
- S2 调 S3/S4 时使用 `RestClient`，响应反序列化为 `JsonNode`（S2 不依赖 device/alarm 服务的 VO），失败统一抛 `ActionCallException` 记录为执行失败。
- 连接/读取超时配置为 500ms（`smart-home.action.connect-timeout-ms / read-timeout-ms`）。

> ⚠️ 待确认：S1 → S2 调用是否也配置了超时（RuleClient 的 requestFactory 超时值需以 `environment-service` 配置为准，本资料未逐行核对该工厂的超时设置）。

## 2. 技术架构图所需信息

### 2.1 分层结构

```
┌─────────────────────────────────────────────────────────────┐
│  展示层：Vue 3 家属端（5173）  +  ESP32 老人端硬件（HTTP 客户端）│
└───────────────────────────┬─────────────────────────────────┘
                            │ HTTP/JSON（统一走 8080）
┌───────────────────────────▼─────────────────────────────────┐
│  接入层：Spring Cloud Gateway（8080，register-enabled=false） │
│         Path 谓词 → lb://service-name（经 Nacos 解析）       │
└───────────────┬─────────────────────────────────────────────┘
                │  /api/v1/**  （/internal/** 不暴露）
┌───────────────▼─────────────────────────────────────────────┐
│  服务层（Nacos 注册，ip=127.0.0.1 强制注册）：               │
│   S1 环境(8081)  S2 规则(8082)  S3 设备(8083)  S4 告警(8084) │
│   服务间：RestClient 直连 /internal/**                        │
└───────────────┬─────────────────────────────────────────────┘
                │ MyBatis-Plus / JDBC
┌───────────────▼─────────────────────────────────────────────┐
│  数据层：MySQL 8（3306，库 smart_home_db）                    │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 一次请求的完整链路（以「环境自动控制」为例）

```
ESP32 采集 → POST /api/v1/environment/readings
  → Gateway(8080) 路由到 S1
  → S1 入库 environment_data
  → S1 RestClient → S2 POST /internal/rules/evaluate（规则评估）
  → S2 命中规则 → RestClient → S3 POST /internal/device-commands（创建 PENDING 指令）
  → ESP32 每 5s GET /api/v1/device-commands/pending 轮询取指令并执行
  → ESP32 POST /api/v1/device-commands/{id}/result 反馈结果
  → S3 更新指令 SUCCESS/FAILED
  → S2 定时任务回填 rule_execution_log.device_exec_result
  → 前端 GET 查询显示最新状态
```

### 2.3 对外 vs 内部调用区分

- **对外（经网关）**：所有 `/api/v1/**` 接口，前端与 ESP32 均只能走 8080 网关；前端不直连各微服务端口，ESP32 访问的是 `http://电脑局域网IP:8080`（不能用 127.0.0.1）。
- **内部（服务间）**：所有 `/internal/**` 接口，仅微服务之间 RestClient 直连调用，网关不暴露。

### 2.4 Nacos 与 Gateway 的用途

- **Nacos**：仅承担 **服务注册与发现**，供网关的 `lb://service-name` 负载均衡解析目标 IP。S1~S4 注册时强制 `ip: 127.0.0.1`（避免 Windows 多网卡误注册虚拟网卡 IP 导致网关路由失败）。网关自身 `register-enabled: false`，不注册进服务列表。
- **Gateway**：统一对外入口 + 路由转发 + 服务发现客户端。路由清单见第 4 节；负载均衡基于 Spring Cloud LoadBalancer。

## 3. 功能架构

### 3.1 老人端硬件功能（ESP32）

| 功能 | 说明 | 实现方式 |
|---|---|---|
| 环境感知 | 温湿度(XHT11)、气体原始值(MQ-2 数字口)、人体活动(PIR)、水滴(扩展) | 周期采集 → 30s 上报 S1 |
| 设备执行 | 风扇、LED 灯、窗户舵机、门舵机 | 5s 轮询待执行指令并执行 |
| 一键求助 | 实体按键 GPIO32 | 按下 → POST 告警 + 本地蜂鸣器提醒 |
| 心跳保活 | 30s 一次心跳 | 供 S3 在线判定 |

### 3.2 家属端五个页面（Vue 3）

| 页面 | 路由目录 | 功能 |
|---|---|---|
| 家庭总览 | views/dashboard | 环境概况、主控状态、设备概况、安全告警、自动化概况、最近动态（30s 自动刷新） |
| 环境监测 | views/environment | 当前环境 + 历史数据 + 温湿度趋势图 |
| 设备管理 | views/devices | 设备列表、在线状态、风扇/灯/舵机远程控制、指令执行状态 |
| 告警管理 | views/alarms | 一键求助/环境异常告警、状态筛选、PENDING→PROCESSING→PROCESSED |
| 自动化规则 | views/rules | 规则增删改查、启用/停用、执行日志查询 |

### 3.3 四个微服务职责（S1~S4）

| 服务 | 职责 | 主要业务能力 |
|---|---|---|
| S1 environment-service | 环境数据 | 环境上报入库、当前/历史查询、家庭/房间 CRUD、上报后触发规则评估 |
| S2 rule-service | 规则引擎 | 规则 CRUD/启停、条件评估（阈值+连续确认）、动作执行（设备指令/告警）、执行日志、自动关灯定时任务、结果回填 |
| S3 device-service | 设备与指令 | 设备 CRUD、心跳与离线判定、指令创建/查询/结果反馈、远程控制、手动控制保护 |
| S4 alarm-service | 告警 | 一键求助、环境异常告警、告警列表/状态更新 |

### 3.4 功能关联关系

- **环境数据 → 规则**：S1 上报后调用 S2 评估，形成「感知 → 决策」闭环。
- **规则 → 设备指令**：S2 命中规则后调用 S3 创建指令，形成「决策 → 控制」闭环。
- **设备指令 → 硬件**：ESP32 轮询 S3 待执行指令并执行，形成「控制 → 执行」闭环。
- **执行结果 → 日志**：ESP32 反馈结果后，S2 定时回填规则执行日志。
- **求助/告警 → 家属端**：ESP32 求助或规则产生的告警进入 S4，家属端查询并处理。

## 5. 数据库设计

库名 `smart_home_db`；编码 utf8mb4；MyBatis-Plus 开启下划线转驼峰，主键 `id-type: auto`。

### 5.1 表清单（共 9 张，含归属）

| 表名 | 归属服务 | 用途 |
|---|---|---|
| family | S1 | 家庭信息 |
| room | S1 | 房间信息 |
| device | S3 | 设备主数据（含在线/运行状态、心跳） |
| environment_data | S1 | 环境采集数据 |
| automation_rule | S2 | 自动化规则定义 |
| rule_execution_log | S2 | 规则执行日志 |
| device_command | S3 | 设备控制指令 |
| alarm | S4 | 告警记录 |
| auto_light_state | S2 | 自动关灯活动时间状态 |

### 5.2 各表关键字段与关系

| 表 | 关键字段 | 关系 |
|---|---|---|
| family | id, family_name, address, create_time | 1 对多 room |
| room | id, family_id(FK→family), room_name, create_time | 1 对多 device |
| device | id, device_code(UK), device_name, device_type, room_id(FK→room), online_status, device_status, create_time, last_heartbeat_time | 关联 room；device_code 被 environment_data/device_command/alarm 引用 |
| environment_data | id, device_code, temperature, humidity, gas_raw, water, pir_triggered, collect_time | device_code 关联 device |
| automation_rule | id, rule_name, trigger_type, condition_config(JSON), action_config(JSON), enabled, create_time | 1 对多 rule_execution_log |
| rule_execution_log | id, rule_id(FK→automation_rule), trigger_value, evaluation_result, execution_result, execution_time, device_command_id, device_exec_result, failure_reason | 关联规则；device_command_id 关联 device_command |
| device_command | id, command_code(UK), device_code, action, source, status, result_message, create_time, finish_time | device_code 关联 device |
| alarm | id, alarm_code(UK), alarm_type, device_code, alarm_content, alarm_time, status, handle_time | device_code 关联 device |
| auto_light_state | id, device_code(UK), last_activity_time, update_time | 按 device_code 唯一 |

### 5.3 数据关系要点

- **device.device_code** 是贯穿全库的关联键：environment_data、device_command、alarm 均通过 device_code 关联设备（非主键 id 外键，实际为逻辑关联）。
- **rule_execution_log.device_command_id** 把「规则决策」与「设备执行」串起来，用于回填 `device_exec_result`。
- **condition_config / action_config 为 JSON 列**，规则结构：`{metric, operator, threshold[, confirmCount]}` 与 `{actionType: DEVICE_COMMAND|ALARM, ...}`。

> ⚠️ 待确认：`device.device_status`（ON/OFF）为设计期字段，实际运行时「设备是否开启」的权威值是由 **最近一次 SUCCESS 指令推导**（见 `DeviceStateVO`，`action=TURN_ON` 视为开，其余为关），而非直接读 `device_status`。此字段当前属于陈旧字段（代码注释「不读 device.device_status 陈旧字段」）。答辩时建议表述为：运行状态以指令历史推导为准。

   成功标准：串口打印 Wi-Fi 连接成功及 IP；30s 内有环境上报，5s 轮询待执行指令。

## 7. 核心业务流程

### 7.1 环境自动控制（感知→决策→执行→反馈）

以「温度超限自动开风扇」为例：

1. ESP32 每 30s 采集 XHT11 温湿度、MQ-2、PIR 等，`POST /api/v1/environment/readings`（经网关）到 S1。
2. S1 将数据写入 `environment_data` 表。
3. S1 通过 `RestClient` 调 S2 `POST /internal/rules/evaluate`，传入本次读数。
4. S2 加载启用规则，进行条件评估：
   - `confirmCount <= 1` 走边沿触发（单次满足即匹配）；
   - `confirmCount > 1` 走连续确认去抖（如 water_window 需连续 3 次满足才触发）。
5. 若命中（MATCHED），S2 依 `action_config` 执行动作：
   - `DEVICE_COMMAND`：RestClient 调 S3 `POST /internal/device-commands`（source=AUTO_RULE）创建 PENDING 指令，回填 `device_command_id`。
   - `ALARM`：RestClient 调 S4 `POST /internal/alarms` 创建环境异常告警。
6. S3 判断手动控制保护：若 5 分钟内存在相反的 REMOTE 指令，则返回业务码 409，S2 记 `evaluation_result=BLOCKED`（不阻断后续上报，但去抖计数会重置）。
7. ESP32 每 5s `GET /api/v1/device-commands/pending?deviceCode=` 轮询，取到指令后驱动执行器（风扇/灯/窗/门）。
8. ESP32 执行后 `POST /api/v1/device-commands/{id}/result` 反馈 SUCCESS/FAILED；S3 更新指令状态。
9. S2 定时任务（结果回填）按 `device_command_id` 查 S3 指令状态，回填 `rule_execution_log.device_exec_result`。
10. 前端查询规则执行日志、设备状态、环境数据展示最新结果。

### 7.2 一键求助链路

1. 老人按下实体按键 GPIO32（按键消抖，单次按压只发一次请求）。
2. ESP32 `POST /api/v1/alarms/help`（经网关）到 S4。
3. S4 创建 `alarm_type=MANUAL_HELP` 告警（status=PENDING），并本地蜂鸣器提醒。
4. 家属端告警页查询显示该告警。
5. 家属将告警更新为 PROCESSING，处理后更新为 PROCESSED。

### 7.3 手动控制保护（关键机制）

- 当家属远程控制（REMOTE 指令）某执行器后，5 分钟内（`MANUAL_PROTECT_WINDOW_MINUTES=5`）同一执行器方向相反的自动规则指令（AUTO_RULE）会被 S3 拦截（业务码 409）。
- S2 收到 409 后把该次评估记为 BLOCKED，避免「用户手动操作被自动规则立刻覆盖」。

## 9. 项目不足与后续计划

### 9.1 已识别的局限（如实）

1. **无自动化测试**：工程内没有任何 JUnit/接口自动化测试，回归依赖手工联调，测试可重复性弱。
2. **服务间调用直连 IP**：S1→S2、S2→S3/S4 使用 `RestClient` 直连 `127.0.0.1:端口`，未走 Nacos 服务发现，单机固定地址，无法自动故障转移/多实例负载均衡。
3. **MQ-2 未做模拟量采集**：GPIO23 不具备 ADC，当前仅读数字口，只能做阈值触发，无法得到真实燃气浓度值（已在文档中明确「不得把 MQ-2 原始值描述为真实燃气浓度」）。
4. **水滴/语音/RGB/RFID/LCD 未接入**：均为「后续扩展」占位，未实现对应功能。
5. **指令去重为内存态**：ESP32 端 `executedCache[16]` 在内存中维护，重启后丢失，不保证跨重启的「恰好一次」执行。
6. **`device.device_status` 字段陈旧**：实际运行状态由指令历史推导，该字段与真实状态可能不一致。
7. **`schema.sql` 与迁移脚本的幂等性**：seed 脚本已用 `WHERE NOT EXISTS` 做幂等，但历史迁移中的 `ALTER TABLE ... ADD COLUMN` 若重复执行会报错，需注意执行顺序。
8. **前端采用 HTTP 轮询**：未引入 WebSocket，实时性受轮询周期（前端 30s 刷新）限制。
9. **PIR 仅活动检测**：明确「不是跌倒检测」，系统不具心率/医疗诊断能力（已在协作规则中禁止此类表述）。

### 9.2 后续计划

1. 引入 JUnit + 接口自动化测试（Testcontainers 或 MockMvc）建立回归基线。
2. 服务间调用改为 Nacos `lb://` + OpenFeign/RestClient 服务发现，支持多实例与故障转移。
3. 接入 MQ-2 模拟量（换用带 ADC 的引脚/外部 ADC 模块）并做浓度标定。
4. 补齐水滴、语音、RGB、RFID、LCD 等外设接入。
5. ESP32 指令去重改为持久化（如 RTC/NVS 存储已执行指令 ID），保证重启不重复执行。
6. 前端引入 WebSocket/SSE 推送，降低轮询延迟。
7. 统一数据库迁移管理（Flyway/Liquibase）解决脚本幂等与版本管理。
8. 完善「异常与断网」场景测试，形成 7-06 全链路测试报告。
