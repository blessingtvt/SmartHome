# 阶段七：ESP32 硬件接入与 Vue 家属端开发实施说明

## 一、项目背景

本项目为面向老年人的智能家居主动感知系统，采用微服务架构。

现有后端已经完成阶段一至阶段六，包含：

- S1：环境服务，端口 8081
- S2：规则服务，端口 8082
- S3：设备服务，端口 8083
- S4：告警服务，端口 8084
- G0：Gateway 网关，端口 8080
- Nacos：服务注册发现，端口 8848

后端采用 Java 17、Spring Boot 3.2.4、Spring Cloud 2023.0.1、Spring Cloud Alibaba 2023.0.1.0、MyBatis-Plus 3.5.7、MySQL 8。

阶段七不应随意修改已经验收通过的后端业务逻辑、数据库结构和 API 契约。若确实需要修改，必须先说明原因、影响范围和兼容性，再提出方案。

## 二、阶段七总体目标

完成三个部分：

1. ESP32 真实硬件接入。
2. Vue 3 家属端开发。
3. 硬件、前端、网关和后端的端到端联调。

核心业务链路：

环境感知 → 数据上报 → 规则判断 → 创建设备指令 → ESP32 执行 → 执行结果反馈。

求助链路：

老人按下实体按键 → 创建求助告警 → 家属端查看告警 → 家属处理告警。

## 四、ESP32 硬件与开发环境

### 4.1 开发板

- ESP32-WROOM-32 模组。
- Arduino IDE。
- Arduino C/C++。
- Wi-Fi 2.4GHz。
- HTTP + JSON 通信。
- 可以使用 ESP32 内置 FreeRTOS 能力，但初期优先采用 Arduino loop + millis() 定时调度，避免过早引入多任务复杂度。

### 4.2 硬件清单

| 元器件 | 原接线 | 计划用途 |
|---|---|---|
| 130 电机风扇模块 | GPIO19、18 | 模型风扇开关 |
| MQ-2 | GPIO23（D） | 气体传感器原始数据采集 |
| 窗户舵机 | GPIO5 | 模型窗户控制 |
| 门舵机 | GPIO13 | 模型门控制 |
| 黄色 LED | GPIO12 | 模型灯控制 |
| PIR | GPIO14 | 人体活动触发 |
| 智能语音模块 | GPIO16、27 | 后续扩展 |
| XHT11 | GPIO17 | 温湿度采集 |
| 无源蜂鸣器 | GPIO25 | 本地声音提醒 |
| SK6812 RGB | GPIO26 | 状态指示 |
| MFRC522 | 原表标注 I2C | RFID 扩展，接口待核实 |
| LCD1602 | I2C | 本地状态显示 |
| 水滴传感器 | GPIO34 | 水滴检测扩展 |
| 按键一 | GPIO32 | 一键求助 |
| 按键二 | GPIO4 | 后续扩展 |

以上是现有接线资料，不代表最终接线方案。

编写正式程序前，必须审核 ESP32-WROOM-32 的 GPIO 功能、启动绑带引脚、ADC 通道、输入输出限制、电压和外设接口。

特别注意：

1. GPIO23 不具备 ADC 功能，不能直接用于 MQ-2 模拟值采集。
2. GPIO34 是输入专用引脚，没有内部上拉、下拉能力。
3. GPIO12、GPIO5、GPIO4 等涉及启动绑带，需评估外设连接对启动的影响。
4. 常见 MFRC522 使用 SPI，必须核实实际模块接口。
5. 电机必须通过适当驱动电路控制，不能直接连接 ESP32 GPIO。
6. 舵机和电机应使用合适的外部供电，并做好共地。
7. MQ-2 模拟输出不得超过 ESP32 GPIO 的允许电压。
8. 不得未经核实就修改用户现有接线。

首先输出硬件风险分析和建议引脚分配表，等待确认后再编写正式程序。

## 六、ESP32 网络通信规范

ESP32 作为 HTTP 客户端，不再使用原有 WiFiServer 网页服务作为核心通信方式。

统一访问 Gateway：

http://电脑局域网IPv4地址:8080

不能使用 127.0.0.1，因为该地址在 ESP32 上指向 ESP32 自身。

使用 HTTPClient 和 ArduinoJson。

现有接口：

| 功能 | 方法 | 路径 |
|---|---|---|
| 环境数据上报 | POST | /api/v1/environment/readings |
| 待执行指令查询 | GET | /api/v1/device-commands/pending |
| 指令结果反馈 | POST | /api/v1/device-commands/{commandId}/result |
| 一键求助 | POST | /api/v1/alarms/help |
| 设备心跳 | POST | /api/v1/devices/{deviceCode}/heartbeat |

请求体和响应体必须以现有 Java DTO、VO、Controller 为准。

开发前先阅读对应后端代码，禁止猜测字段名、状态值和响应结构。

时间戳使用 Unix 毫秒。

设备编码使用数据库中实际创建的 deviceCode，例如 ESP32_001。具体编码以数据库记录为准。

## 七、ESP32 功能开发顺序

### 7-01 硬件单模块测试

先完成：

- Wi-Fi 连接与串口输出 IP。
- XHT11 温湿度读取。
- MQ-2 读取。
- PIR 活动检测。
- 按键检测。
- LED 控制。
- 蜂鸣器控制。
- 风扇驱动。
- 舵机控制。
- LCD 显示。

每个模块单独编译、烧录和测试，记录实际引脚与测试结果。

### 7-02 环境数据上报

实现：

- Wi-Fi 自动重连。
- 传感器周期采集。
- JSON 组装。
- HTTP POST 到 S1。
- 请求超时和错误处理。
- 串口输出请求状态和响应结果。

验收：真实传感器数据成功进入 environment_data 表。

### 7-03 设备指令执行

实现：

- 定时轮询待执行指令。
- 解析 deviceCode、commandId、action。
- 根据设备编码和动作映射执行器。
- 支持 TURN_ON 和 TURN_OFF。
- 执行后调用结果反馈接口。
- 只有实际执行成功才反馈 SUCCESS。
- 不支持的动作或执行失败反馈 FAILED。

验收：后端创建 PENDING 指令，ESP32 实际执行后，S3 状态更新为 SUCCESS 或 FAILED。

注意：具体指令 JSON 字段必须以 S3 当前代码为准。

### 7-04 一键求助和本地交互

实现：

- 按键消抖。
- 单次按压只产生一次求助请求。
- POST 到 API04。
- 蜂鸣器本地提醒。
- LCD 显示求助状态。
- 网络异常时提供明确提示，避免误报请求成功。

### 7-05 设备心跳和运行稳定性

- 每 30 秒发送一次设备心跳。
- 处理 Wi-Fi 断开。
- 网络恢复后重新连接。
- 避免阻塞式长时间 delay。
- 避免重复执行同一条指令。
- 处理 HTTP 超时和 JSON 解析失败。

## 九、阶段七整体验收场景

### 场景一：真实环境自动控制

1. ESP32 采集温度。
2. 上报 S1。
3. S1 通知 S2。
4. S2 匹配温度规则。
5. S3 创建风扇 TURN_ON 指令。
6. ESP32 轮询到指令并启动风扇。
7. ESP32 上报执行结果。
8. S3 更新 SUCCESS。
9. Vue 家属端显示环境和设备状态。

### 场景二：一键求助

1. 老人按下实体按键。
2. ESP32 向 S4 发送求助请求。
3. S4 创建 MANUAL_HELP 告警。
4. Vue 家属端显示告警。
5. 家属将告警更新为 PROCESSING。
6. 处理完成后更新为 PROCESSED。

### 场景三：家属远程控制

1. 家属在 Vue 页面点击风扇开启。
2. Vue 调用 Gateway。
3. S3 创建 PENDING 指令。
4. ESP32 轮询并执行。
5. ESP32 上报 SUCCESS。
6. 前端刷新显示最新状态。

### 场景四：异常和断网

测试：

- ESP32 Wi-Fi 断开。
- Nacos 或 Gateway 不可用。
- 传感器读取失败。
- HTTP 请求超时。
- 指令反馈失败。
- ESP32 重启。
- 设备离线检测。

## 十、编码协作规则

Claude 必须遵循：

1. 每次只实现一个子任务。
2. 编码前先阅读相关代码和接口。
3. 不得擅自修改已验收的后端业务代码。
4. 不得擅自修改数据库 schema。
5. 不得虚构硬件能力。
6. 不得把 MQ-2 原始值描述为真实燃气浓度。
7. 不得把 PIR 活动检测描述为跌倒检测。
8. 不得声称系统具备心率监测或医疗诊断能力。
9. 不得直接用 ESP32 GPIO 驱动电机或大功率负载。
10. 不得把设备指令创建成功等同于硬件执行成功。
11. 每个子任务完成后提供修改文件清单、编译方法、测试方法和测试结果。
12. 不确定的硬件参数和 API 字段必须先提出问题，不允许自行猜测。
13. 所有代码必须给出完整文件内容或清晰 diff，不能只给片段而不说明放置位置。
